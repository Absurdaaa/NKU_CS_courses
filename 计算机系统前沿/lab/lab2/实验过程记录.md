## 任务一：参数调优结果

### 1. `write_buffer_size` 对比

| 配置 | QPS | P50(us) | P90(us) | P99(us) | P99.9(us) |
| --- | ---: | ---: | ---: | ---: | ---: |
| `4MB`  | 107122 | 0.856 | 6.459 | 19.442 | 1169.580 |
| `16MB` | 379596 | 0.649 | 3.534 | 9.015 | 18.560 |
| `64MB` | 361690 | 0.673 | 3.363 | 7.842 | 18.473 |

结论：

- `4MB -> 16MB` 提升最明显，QPS 提升约 `3.54x`，尾延迟也显著下降，说明小 MemTable 更容易频繁 flush / compaction，前台写放大更严重。
- `16MB -> 64MB` 没有继续提升 QPS，说明在本机负载下 `16MB` 已经接近比较好的平衡点；再增大缓冲区能稍微压低 `P99`，但总体吞吐并未继续上涨。

### 2. `block_size` 对比

| 配置 | QPS | P50(us) | P90(us) | P99(us) | P99.9(us) |
| --- | ---: | ---: | ---: | ---: | ---: |
| `4KB`  | 379596 | 0.649 | 3.534 | 9.015 | 18.560 |
| `16KB` | 334139 | 0.672 | 3.697 | 9.481 | 18.397 |
| `64KB` | 247122 | 0.639 | 3.666 | 10.559 | 20.810 |

结论：

- 在这组热点混合负载下，`4KB` 最优。
- `block_size` 变大后，单次读取和缓存管理的粒度也随之变大，点查会拖入更多无关数据，导致缓存利用率变差，QPS 下降。
- `64KB` 的下降最明显，说明读放大已经超过了减少索引项数量带来的收益。

### 3. Bloom Filter 对比（`uniform` 100% 随机读）

| 配置 | QPS | P50(us) | P90(us) | P99(us) | P99.9(us) |
| --- | ---: | ---: | ---: | ---: | ---: |
| 关闭 Bloom | 394140 | 1.790 | 4.378 | 6.304 | 18.244 |
| 开启 Bloom(`10 bits/key`) | 318702 | 2.206 | 4.827 | 6.719 | 18.463 |

结论：

- 这组实验里 Bloom Filter 没有带来提升，反而略慢。
- 原因不是 Bloom 无效，而是当前测试几乎全部是“命中查询”；Bloom Filter 更擅长加速“不存在 key”的负查询，纯命中场景下会增加一次额外判断开销。
- 因此报告里应明确说明：Bloom Filter 是否有效，取决于 miss 比例，而不是总能提高随机读性能。

## 任务二：长尾延迟与 Compaction 观察

实验命令核心参数：

- `mode=write_only`
- `write_buffer_size=4MB`
- `load_keys=2200000`
- `num_keys=8000000`
- `run_ops=1500000`
- `run_pattern=uniform`

结果摘要：

| 指标 | 数值 |
| --- | ---: |
| QPS | 3036.58 |
| P50(us) | 6.531 |
| P90(us) | 1175.000 |
| P99(us) | 1214.330 |
| P99.9(us) | 1957.830 |

时间线中观察到的典型尖峰：

- `107828us`
- `163212us`
- `2130573us`
- `5168699us`
- `6579167us`
- `7173489us`
- `7264447us`
- `11473789us`

结论：

- 常态写延迟大约在 `1.1ms` 左右，但会周期性出现 `10^5 us` 到 `10^7 us` 级别的停顿，典型地反映了 LSM compaction 的后台压力向前台写入传播。
- `P50` 很低而 `P90/P99/P99.9` 明显抬高，说明系统大部分时间很快，但少数 stall 极其严重，这正是尾延迟问题的核心。
- 这些毛刺通常来自：
  - MemTable flush 触发新的 SSTable 落盘
  - L0 文件过多导致 compaction 跟不上
  - compaction 抢占磁盘 I/O 和 CPU，导致前台写线程等待
  - 当层级压力继续累积时，甚至会出现秒级暂停

环境约束说明：

- 作业要求希望数据集大于物理内存 `2x`。
- 该机器物理内存约 `125G`，理论上需要 `250G+` 的可写磁盘空间。
- 实际可用空间只有根分区 `14G` 与 `/mnt/sdb` 的 `168G`，因此无法满足该硬性上限。
- 本次实验退而求其次，使用尽可能大的可用磁盘并保留完整时间线，仍成功观察到显著的 compaction write stall。

## 任务三：KV Cache vs Block Cache

缓存配置：

- 情景 A：纯 Block Cache
  - `block_cache_size=256MB`
  - `fill_cache=true`
  - `use_kv_cache=false`
- 情景 B：纯 KV Cache
  - `block_cache_size=1`
  - `fill_cache=false`
  - `use_kv_cache=true`
  - `kv_cache_capacity=256MB`

### 1. 点查（Point Get）

| 配置 | QPS | P50(us) | KV Cache 命中 |
| --- | ---: | ---: | ---: |
| Block Cache | 686025 | 0.896 | 0 |
| KV Cache | 1134100 | 0.094 | 84873 |

结论：

- 点查场景下，KV Cache 明显更强，QPS 约为 Block Cache 的 `1.65x`。
- 原因是 KV Cache 以完整键值对为粒度，命中后不需要再走 SSTable block 解析、索引查找和解码路径。

### 2. 范围查询（Range Scan, 32 keys）

| 配置 | QPS | P50(us) | P99(us) |
| --- | ---: | ---: | ---: |
| Block Cache | 114946 | 7.551 | 19.727 |
| KV Cache | 119154 | 7.295 | 18.270 |

结论：

- 两者差距很小，KV Cache 只略高一点。
- 范围查询本质上按 block 连续迭代，Block Cache 的设计天然贴合这个访问模式；KV Cache 并不会像点查那样显著占优。

### 3. 读写混合（80% 读 + 20% 写）

| 配置 | QPS | P50(us) | P99(us) | KV Cache 命中 |
| --- | ---: | ---: | ---: | ---: |
| Block Cache | 477359 | 0.623 | 7.993 | 0 |
| KV Cache | 531167 | 0.357 | 8.593 | 54325 |

结论：

- 混合负载下 KV Cache 仍略优，QPS 约提升 `11.3%`。
- 但优势明显小于纯点查场景，因为写操作会引入缓存失效，KV Cache 的命中率不如纯读高。

## 综合结论

1. `write_buffer_size` 对写密集或混合负载影响很大，小 MemTable 容易触发更频繁的 flush / compaction，带来吞吐下降和尾延迟恶化。
2. `block_size` 并非越大越好；对点查占比高的负载，小 block 往往能减少无效数据搬运。
3. Bloom Filter 对“负查询”更有价值；若查询几乎全命中，可能看不到收益。
4. Compaction 是尾延迟的主要来源，均值和中位数都不足以描述真实写体验，必须看高分位和时间线。
5. 点查场景下，应用层 KV Cache 明显强于 Block Cache；扫描场景两者更接近，因为 Block Cache 的数据块粒度与 scan 更匹配。
