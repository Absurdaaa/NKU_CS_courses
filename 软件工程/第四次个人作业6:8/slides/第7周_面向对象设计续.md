# 开闭原则(Open/Closed Principle, OCP)

最初由Bertrand Meyer提出

<span style="color:#c00000">软件实体在扩展性方面应该是开放的，而在更改性方面应该是封闭的。</span>

例：打印输出设计

---

人们常常提到的四项面向对象设计的原则，包括开闭原则、里氏替换原则、依赖倒置原则和接口分离原则。其中开闭原则是最能反映面向对象设计的目的的。他主要的思想是软件实体要在扩展性方面保持开放，而在更改行方面应该是保持封闭的。也就是说应该尽量使得软件系统是可扩展的，而在扩展的过程中，不需要对源代码进行修改。为了实现开闭原则，我们就要尽可能多的使用接口进行封装，采用抽象机制，运用多态技术。比如在这两个类图里，设计1就是将输出操作直接定义为与具体的某种输出设备直接关联的形式，而设计2就在输出和具体的设备之间定义了一个抽象接口，叫print，通过在中间层次引入一个抽象接口，可以使得我们的软件实体中当出现新的设备类时，我们可以用新设备来实现这个接口，而不需要修改Output这个客户端的对象相关的源代码，从而实现在扩展性方面开放，而在更改性上封闭。因此设计2的接口更加符合我们倡导的满足开闭原则.

# Liskov Substitution Principle (LSP)

最早由 __Liskov__ 于1987年在OOPSLA会议上提出

<span style="color:#800000">子类可以替换父类出现在父类能出现的任何地方</span>

---

第二个原则就是里氏替换原则，即任何基类出现的地方都应该可以无差别的使用子类替换。通俗地讲，就是子类型能够完全替换父类型，而不会让调用父类型的客户程序从行为上有任何改变。在面向对象设计中，我们有了继承和泛化的概念，继承的优点是大大提升了代码的复用度，但是它的缺点也同样明显：增加了对象的耦合程度，破坏了程序的封装性，导致程序的可移植性变差。这里耦合可以简单理解为相互影响、相互作用。继承容易破环程序的封装性，而使用里氏替换原则可以大大减少我们代码的出错概率。这么说可能比较抽象。

下面我们来看一个违反里氏替换原则的例子。如果我们将正方形作为长方形类的一个子类，那么我们应该如何定义正方形类中设置边长的方法呢？

# 解决方法

public class  <span style="color:#ff0000">Square</span>   <span style="color:#ff0000"> __extends__ </span>   <span style="color:#ff0000">Rectangle</span>  \{  public void setWidth\(int width\) \{

super\.setWidth\(width\);  super\.setHeight\(width\);

\}

public void setHeight\(int height\) \{  super\.setHeight\(height\);  super\.setWidth\(height\);

\}

---

首先我们看第一个解决方法，这里由于正方形继承了长方形类，我们将正方形中边长的设置定义为在设置长和设置宽的方法里，实际上都将正方形的长宽设置为跟参数一样。那么这个方法是否满足里氏替换原则呢？

# 思考题：如何知道子类的行为符合父类的要求？

契约式设计 \(Design by Contract\)

为了满足Liskov替换原则，设计时要求：

子类中方法的前置条件不能强于父类中相应方法的前置条件。

子类中方法的后置条件不能弱于父类中相应方法的后置条件。

<span style="color:#800000">Liskov</span>  <span style="color:#800000"> </span>  <span style="color:#941100">替换原则要求子类宽入严出！</span>

---

那么我们如何知道子类的行为是符合父类的上下文场景要求的呢。其实契约式设计是一个比较好的设计方法。也就是说我们在设计时，要明确的了解外部环境对子类和父类的前置条件和后置条件的要求。满足里氏替换原则的设计要求是，子类方法的前置条件不能强于父类方法的前置条件，子类方法的后置。。。也就是说，里氏替换原则要求子类的行为宽入严出。通俗的说，从调用父类的客户程序的角度来说，它关心的仅仅是父类的行 为，只要可以在任何父类出现的地方用子类来替代，而不影响父类本来的行为，那么就不算是违背该原则。因此，我们在设计过程中子类可以扩展新功能，但是尽量不要重写/重载父类的接口，导致父类不可被子类替换。另一方面，当我们发现父类拥有子类不希望继承，或者勉强继承会对子类造成破坏时 ，正可以说明这个继承体系可能存在问题。简单来说，子类并不关心父类的行为，但却需要遵循父类制定的规范或契约，以满足客户调用父类的期望。如果前人制定的规范我们不遵循，反而要去打破，那就不是继承，而是要另起炉灶了。显然，里氏替换原则对于约束继承的泛滥具有重要意义。

# 依赖倒置原则 (Dependency Inversion Principle, DIP)

依赖倒置原则指的是依赖关系应该是尽量依赖接口\(或抽象类\)，而不是依赖于具体类。

---

第三个原则是依赖倒置原则，它是指我们在建立依赖关系时，应该尽量以来抽象的接口或者抽象类，而不是。。我们之前学过结构化设计，从结构化设计中。。。可以看出主程序依赖几个大的模块，每个大模块又依赖几个更细的模块。这与依赖倒置原则中尽量。。而不是。。是背道而驰的。

# 面向对象设计中的依赖关系

---

面向对象中的依赖关系强调在顶层具体的客户类之间和具体类之间建立抽象的接口和抽象类，这样我们就能够确保无论是程序应用场景发生变化，还是底层的具体实现发生变化，都能够保证中间程序结构的稳定性，确保软件正常演化。

# 接口分离原则(Interface Segregation Principle, ISP)

在设计时采用多个和特定客户类\(client\)有关的接口要比采用一个通用的接口要好。

---

最后接口分离原则是说我们在设计时要建立比较小的接口，要采用多个和特定。。接口分离原则只是一个相对的建议，使用通用的接口，其好处是对客户端来说，只需要知道一个接口的信息就好，但是采用分离接口就意味着每个接口的修改，其影响范围比较小，不容易牵一发而动全身。这是一个权衡的过程。

表达整体与部分结构的是聚合和组合关系。他是关联关系的一个特例。聚合关系表达的是一个整体对象和它的成员对象之间的关系。聚合关系中代表部分事物的对象，是可以属于多个对象的，也就是说，一个部分对象是可以被多个整体对象所共享的。它还可以随时改变它所从属的整体对象。部分对象和整体对象的生存期是无关的。一旦删除了它的聚合对象，也就是整体对象，它的部分对象还是存在的。这就是聚合关系。而组合关系是聚合的一个特例，它所代表的是一个整体对象和部分组成之间的关系，二者之间的所属关系更强，当整体对象不存在时，部分类的对象也不再存在。反之亦然，整体类对象撤销之前，要将它所有的部分类对象撤销。也就是说代表整体事物的组合对象，要负责创建和删除代表部分对象的成员。代表部分对象的事物只能从属于一个整体对象，而不能从属于多个对象，一旦删除了整体，部分也随之消除。这就是组合关系。在确定了类的行为和属性之后，其实很容易对聚合和组合关系进行区分的。比如一个窗口和他附属的按钮，应该是组合关系，因为二者具有相同的生命周期，一个的破坏会导致另一个的消亡。反之，一个由同类元素组成的集合，比如一组照片，和他的个体元素，也就是每张照片，应该是一个聚合关系，因为照片集和照片的创建和消亡并不同步，一个照片也可以从属于多个照片集。在生成代码的时候，我们需要为组合关系类考虑同步问题，而聚合关系则不需要。聚合关系它的实例之间是由传递关系的，是一个偏序关系，那么聚合和关联关系的区别在于，聚合关系的实例是不能形成环的。运用聚合和组合简化了对象的定义，更好地支持软件重用。在后面的介绍中，我们会知道，其实这种组合关系要比继承关系应用起来更加灵活方便。在这张图中，我们可以看到我们将汽车和他的引擎定义为组合关系，因为汽车和引擎的生存周期由很强的绑定关系，而左边的汽车和驾驶员之间是聚合关系，他们的关系是临时性的，谁都可以临时开车，一辆车必须有且只有一个驾驶员，因此在驾驶员这一端的维度定义为1，而一个人并不一定要开一辆车，开也最多开一辆，因此在汽车的一端是可选关联，用01表示。再看右边的火车，一辆火车一定要有至少一个火车头，火车和火车头之间是组合关系，但是火车与乘客之间是聚合关系，乘客上下车，与火车之间的关系是动态变化的，生存周期也并不绑定。一辆火车可以有也可以没有乘客，因此在乘客的这一段多样性是0·N，但是一个乘客要么不上火车，上也只能同时上一辆火车，因此在火车的一端是多样性定义是0-1，也就是可选的关联关系。

# 继承/泛化(Inheritance/Generalization)



* <span style="color:#800000">子类继承父类的属性</span>  <span style="color:#941100">、</span>  <span style="color:#800000">关联和操作</span>
* 子类可以 <span style="color:#800000">覆盖</span> 继承来的内容
* 例如：行政员工 __AdminStaﬀ__ 和专业 设计人员 __CreativeStaﬀ__ 的奖金计算 方法可以不同
* 父类可以声明为 <span style="color:#800000">抽象类</span> \{ <span style="color:#800000"> __abstract__ </span> \}，则 将不会为它直接创建实例对象
  * 意味着现有子类覆盖了该类对象 的 <span style="color:#800000">全集</span>
* 例如，除了行政员工 __AdminStaﬀ__ 和 专业设计人员 __CreativeStaﬀ__ 之外，  不存在其他类员工

# 类图建模风格

1：属性名和类型应该一致

2：不要对有关联类的关联关系进行命名。

3：静态操作/属性要在实例操作/属性之前列出。

4：以可见性降低的次序列出操作/属性。

5：避免已被语言的命名规范所隐含的版型。

6：总是指明多样性

7：不要对每个依赖关系都建模

8：将子类放在父类的下方

9：小心基于数据的继承

10：按惯例是把整体画在部分的左边

---

在类图建模的过程中，我们给出以下对类图建模风格的建议。首先，尽量保持类属性的名字和类型的一致性。比如如果我们声明的名字是getNumber，那么它的值应该是数值型而不应该是字符串，否则会让人有误解。另外，我们不要对。。。因为关联类本身的名字就是形容关联关系的，就没必要额外增加修饰。其次，静态的操作。。。按照可见性降低的次序。。。，因为可见性高的属性和操作，外人通常更感兴趣。我们还要避免使用那些已经在命名规范中隐含了的版型，比如右上角中constructer..getter,setter的声明就是多余的。另外在关联关系定义过程中，我们要指明多样性，对于聚合和组合关系，如果多样性是1，也可以标明出来，说明在建模过程中考虑到了关系的维度。我们不要对。。。，这样会让我们的类图非常复杂，子类要放在父类的下面。我们还要小心基于。。如果两个类存在关系的唯一原因是他们有公共的数据属性，那么我们一定是遗漏了某些公共的行为，要么我们就应该使用关联关系，而不是继承关系。建模过程中按照管理。。。例如，Team和airplaine分别是。。的整体类，我们按照这样的惯例阅读起来更方便。

<span style="color:#941100">框</span>  <span style="color:#941100">（Frame）</span> ：框中包含顺序图的部分结构，表示选择\(selection\)或者 循环\(loop\)结构，左上角注明结构类型，\[\]中注明条件。

UML2.0中引入了组合框的概念，来表达更为复杂的控制结构。通过把顺序图中一部分交互内容放入框中，并在左上角注明该控制结构的类型，并在方括号中加上控制条件，我们就能够表达选择、循环、并发等更为复杂的控制逻辑。比如下面最左边的这张图，左上角有个opt标志，表明这是一个单一条件的选择结构。当条件满足时，执行框中的交互活动；否则不执行。中间这幅图，左上角有个alt标志，这个同样也表示一个选择结构，不过这个选择结构由两个分支语句，分别在框的上半部和下半部，用虚线隔开。这两部分都有用方括号括起来的各自的控制条件，只有当控制条件满足时，才能执行相应部分的内容。比如这个例子中，当balance<100时，执行上半部分内容；当balance>=100时，执行下半部分的内容。同样是中间这幅图，当我们把左上角的标志从alt改为par时，表示这幅图是一个并发执行的控制逻辑，也就是虚线上下的两部分将并发完成。右边的图中表示的是一个循环控制结构，左上角标志位loop，当方括号内的条件满足时，框中的交互将循环执行。从这里我们可以看出，组合框是一个表达能力很强的建模机制，通过引入框，我们能够更好地表达某一个控制单元的反复执行、选择执行和并发执行。

---

这里我们给出一个简化了的控制结构建模的例子。在这个例子中，我们主要涉及两个参与者，一个是Person，一个是银行ATM机器。我们将整个顺序图放入一个框中，用左上角sd withdrawal表示这是一个名叫withdrawal的顺序图，其中sq是sequence diagram，也就是顺序图的缩写，withdrawal则表示这个顺序图表示的是一个取款过程。这个例子包括一些控制操作符。我们从上往下沿着生命线或者时间轴来看交互消息。首先，由用户启动整个交互序列，我们看到了第一个操作符loop(1,3)，这是一个循环操作符，1和3分别表示循环之心的最少次数和最多次数。因为是最少一次，所以在考虑方括号表示的控制条件之前，第一个组合框中的交互行为至少要执行一次。在这个循环内，用户要输入密码，然后系统验证密码是否正确。如果密码不正确，则继续重复这个交互行为，直到循环3次为止。第二个组合框是一个选择框，左上角有一个opt标志，表示如果此时密码正确，则执行这个组合框中的交互行为，否则将跳过这部分，直接执行后面的内容。在第二个选择组合框中，我们可以看到还嵌套了一个并行组合框，左上角有par的标志。在并行组合框中，有两个分区，上面一个是让用户输入账号，下面一个是让用户输入数额，由于这两个分区是并行关系，所以我们并没有规定要按照什么顺序来输入这两部分的内容。这里我们需要注意的是，并发其实并不意味着物理上一定要同时执行，它想表达的其实是虽然在顺序图中的时间轴上，他们一个在上面一个在下面，但其实这两个控制逻辑之间没有一个明显的次序关系，如果他们确实是两个独立的操作，那么我们就可以交叉执行。如果是顺序的动作，那我们也可以按照任意的次序执行。一旦并行操作的两个动作都执行完成，那么这个并行操作也就执行完毕，我们继续执行下一部分的内容，也就是最底下由ATM向用户传递现金这个交互行为。通过这样的控制结构，我们可以看到，原本只能表达单层的控制顺序，现在可以表达交叠的、多层次的控制顺序，这对我们未来建模更为复杂的控制逻辑有帮助。

# 顺序图建模风格



* 建模风格1：把注意力集中于关键的交互。
  * 创建模型时要把注意力集中于系统的关键方面，而不要包括无关的细节。
* <span style="color:#000000">如果顺序图是用于描述业务逻辑的，就没必要包括对象和数据库之间 的详细交互。</span>
---

顺序图的建模过程中，我们要把主要的注意力集中在关键的交互上，而要把无关的或者不重要的细节忽略掉。比如，如果我们绘制顺序图的主要目的是描述业务逻辑，那么我们就没必要包括对象和数据库之间频繁的详细的交互过程，可能指包括像保存、删除这样的消息就足够了，甚至我们可以持久化问题已经被妥善的处理，而不用考虑持久性相关的每一个细节。





* <span style="color:#434dd6">建模风格2：对于参数，优先考虑使用参数名而不是参数类型。</span>
  * 例如
* 消息  <span style="color:#800000">addDeposit\(amount\,</span>  <span style="color:#800000"> </span>  <span style="color:#800000">target\)</span> 比  <span style="color:#800000">addDeposit\(Currency\,</span>  <span style="color:#800000"> </span>  <span style="color:#800000">Account\)</span>  <span style="color:#800000"> </span> 传递了更多的信息
  * 在消息中只使用类型信息不能传递足够的信息
  * 参数的类型信息用UML类图表示更好
---

在顺序图的建模过程中，我们要有限考虑使用。。。比如，我们将消息addDeposit的参数写作。。比。。要能够传递更丰富的信息，因为前者可以告诉我们，当我们需要存款时，我们要直到存款的数额和目标账户，而通过后者，我们只能够直到这个消息的参数类型是一个现金类和一个账户类，而并不能传递足够的关于领域业务的信息。关于参数的类型，我们最好是在UML的类图中定义。我们要注意，这里的建模风格实际上只是一个建议，而并不是严格的规定，也就是说，当我们需要表示这里要传递的是某种类型的对象时，指明参数类型作为占位符也是可以的。



<span style="color:#434dd6">建模风格3：不要对明显的返回值建模。</span>

<span style="color:#434dd6">建模风格4：可以把返回值建模为方法调用的一部分。</span>

---

除此以外，在顺序图建模时，我们不要对那些明显的返回值进行建模。添加返回消息。比如在这个顺序图中，创建安全登陆对象Security Login,这个行为会导致生成一个新的顾客对象，这个返回值是不明显的，而且我们需要返回新建顾客的ID，此时我们需要对它进行建模，给出一个返回消息，用来返回Customer的ID。而向订单对象发送请求，计算总数，那么它的返回值是显而易见的，需要返回一个总数，此时我们就不需要再对他进行建模了。我们需要注意的是，返回消息，它实际上是同步消息的一部分，比如这个例子里发送getTotal()这个消息之后，其实就是调用了Order的getTotal的操作，调用后一定会有一个返回值，这就是同步消息的一部分。而对于异步消息，大家还记得前面拨打电话的例子，一个人打电话，需要等到另一个人接电话才能够确认会话连同，这就是一个异步消息，不难发现，异步消息的返回值其实是另一个消息了。

# 控制焦点(focus of control)的嵌套

嵌套的FOC可以更精确地说明消息的开始和结束位置。

图例：

<span style="color:#800000">激活期</span> \( <span style="color:#800000"> __ac__ </span>  <span style="color:#800000"> __tivat__ </span>  <span style="color:#800000"> __i__ </span>  <span style="color:#800000"> __o__ </span>  <span style="color:#800000"> __n__ </span> \)：表示对象执行一个动作的期间（直接操作或者通过下级操 作），也即对象激活的时间段。

<span style="color:#800000">控制焦点</span> 和 <span style="color:#800000">激活期</span> 是同一个概念。

---

控制焦点的建模是一个可选项，也就是说我们实际上可以不画出对象的控制焦点和激活器。但是，通过画出控制焦点，我们可以更明确的说明一个消息的开始和结束位置。比如在这个图中，对象1调用了对象2的操作1，然后对象2在执行操作1期间又反过来调用了对象1的操作2，通过增加控制焦点的嵌套机制，我们就可以更精确地说明消息的开始和结束位置，仿佛是一个消息调用的压栈机制。激活期表示的是对象在执行一个动作的期间，它和控制焦点实际上是同一个概念。总的来说，我们可以看着附图中竖直的虚线表示对象的生命线，除非像前面所说的生命线上出现一个差，此时表示该对象被撤销了，对象不再存在。否则对象在生命线期间一直存在。而在虚线上的竖直方框则表示对象的激活期，也就是执行动作的期间。最后，激活期上所出现的消息位置，也就是控制焦点，能够更精确地说明消息地开始和结束位置。比如我们从这幅图中可以看出，一开始对象1调用对象2地操作1，然后在对象2执行操作1期间，对象2又调用了对象1 的操作2，此时操作2所出现的控制焦点其实是在对象1的激活期中间的，这体现了对象1在调用操作1期间，执行了操作2。最后在对象1执行完操作2后又调用了对象3的操作3.
