## 第一周：软件工程课程介绍

**文件名**：`第一周_软件工程课程介绍.md`

### 📖 主要内容

#### 1. 课程介绍与要求

- 课堂要求：电子设备静音，鼓励积极参与讨论
- 作业类型：文档类、代码、个人项目、团队项目（5-10人）
- 考核方式：考勤（15分，3次不到扣全分）+ 作业质量

#### 2. 课程内容框架

```
软件工程学概述
├── 概念定义：软件工程、软件生命周期
├── 软件流程：需求分析、系统设计、编码、测试、维护
└── 开发模型：瀑布模型、敏捷开发模型
```

#### 3. 什么是软件？

**定义**：软件 = 程序 + 数据 + 文档

**软件特性**：

- **复杂性**：Linux内核有630个函数，1814个调用；Google建立在100万台服务器上
- **不可见性**：工程师无法看到源代码如何在用户机器上执行
- **易变性**：软件看起来容易修改，但正确修改很困难
- **非连续性**：小输入变化可能导致大输出变化

#### 4. 什么是软件工程？

**定义**：将系统的、有序的、可量化的方法应用到软件的开发、运营和维护上的过程

**核心领域**：

- 软件需求分析
- 软件设计
- 软件构建
- 软件测试
- 软件维护

#### 5. 软件开发面临的挑战

- 成功率仅约30%
- 典型失败案例：
  - Ariane 5火箭爆炸（64位转16位整数溢出）
  - Windows Vista系统（60亿美元，5年，5000万行代码）
  - 12306购票系统（春运时崩溃）

#### 6. 软件质量

**质量不等于零缺陷**：商业目标决定质量目标

- 质量有成本，不能不惜一切代价追求完美
- 理想目标：让广大用户满意

#### 7. 学习资源

- **教材**：《软件工程》第10版，Ian Sommerville著
- **参考书**：《构建之法》，邹欣著

## 第二周：软件工程导论

**文件名**：`第二周_软件工程导论.md`

### 🎯 核心主题

软件工程的基本概念、目的、质量模型及开发策略

### 📖 主要内容

#### 1. 软件工程发展史

```
史前时代 (1956-1967)：软件开发无方法
├── 1968年：NATO会议首次提出"软件工程"
├── 结构化开发方法，瀑布模型
├── 面向对象开发，CMM/ISO9000质量标准
└── 1990年至今：敏捷开发方法流行
```

#### 2. 什么是软件工程师？

**角色定位**：从客户需求到编程实现之间的桥梁

**主要职责**：

- 了解待开发软件的准确需求
- 规划、设计、开发和维护软件系统

#### 3. 软件质量模型（ISO 9126）

| 质量属性 | 子属性 |
|---------|-------|
| **功能性** | 适合性、准确性、互操作性、安全性 |
| **可靠性** | 成熟性、容错性、可恢复性 |
| **易用性** | 易理解性、易学性、易操作性、吸引性 |
| **效率** | 时间特性、资源利用 |
| **可维护性** | 易分析性、易改变性、稳定性、易测试性 |
| **可移植性** | 适应性、易安装性、共存性、替换性 |

#### 4. 软件开发基本策略

1. **软件复用**：直接复用已有构件，提高质量和效率
2. **分而治之**：将复杂问题分解为可理解的子问题
3. **逐步演进**：迭代式增量开发
4. **优化折中**：协调各质量特性，实现整体最优

#### 5. 软件工程三要素

```
过程：支持软件开发各环节的控制和管理
方法：完成开发任务的技术手段
工具：提供自动或半自动的支撑环境
```

#### 6. 个人软件过程（PSP）

演进版本：PSP0 → PSP0.1 → PSP1 → PSP1.1 → PSP2 → PSP2.1

核心度量指标：

- Size：代码规模（LOC）
- Effort：时间（分钟）
- Quality：缺陷数
- Schedule：进度

## 第3周：需求分析

**文件名**：`第3周_需求分析.md`

### 🎯 核心主题

需求工程的概念、分类、获取技术

### 📖 主要内容

#### 1. 需求定义

**IEEE定义**：需求是人们要解决的某个问题或达到某种目的的需要

**需求管理三项任务**（Alan M. Davis）：

- 学习 — 需求获取
- 剪枝 — 需求优选
- 文档化 — 撰写需求规格说明书

#### 2. 需求分类

**按对象划分**：

```
产品需求
├── 功能性需求
└── 非功能性需求
    ├── 服务质量（性能、可靠性、安全性等）
    ├── 依从性
    ├── 体系结构约束
    └── 设计开发约束

过程需求
```

**按抽象层次划分**：

- 业务需求（组织目标）
- 系统需求（从用户角度描述系统功能）
- 用户需求（影响用户接受程度的需求）
- 软件设计规约

#### 3. 需求工程活动

```
需求抽取 (Elicitation)
    ↓
需求分析 (Analysis)
    ↓
需求规约 (Specification)
    ↓
需求验证 (Validation)
    ↓
需求管理 (Management)
```

#### 4. 四世界模型

- **主题世界**：系统的主题内容（如顾客、账号、交易）
- **应用世界**：操作环境、人和企业流程
- **系统世界**：系统内部操作、数据库、报告
- **开发世界**：开发过程、团队、进度、质量要求

#### 5. 需求获取技术

- **面谈**：有组织的面谈、自由面谈
- **问卷调查**：面向大基数被访者
- **群体诱导技术**：3-20人，头脑风暴、专题小组
- **原型法**：明确含糊需求，获得早期反馈
- **文档分析**：分析现有系统、规章制度

## 第4周：需求分析

**文件名**：`第4周_需求分析.md`

### 🎯 核心主题

需求获取技术详解、需求验证、需求文档

### 📖 主要内容

#### 1. 需求获取技术详解

**面谈技巧**：

- 轻松开场（天气、体育等）
- 先问简单问题（个人信息）
- 避免诱导性问题，鼓励讲故事

**问卷调查**：

- 适用场景：大基数、远程、验证面谈结论
- 注意事项：避免样本偏见、问题设计妥当性

**群体诱导**：

- 专题小组会议、头脑风暴
- 原则：百花齐放、不评价、不争论

**参与观察法**：

- 观察者参与被观察对象日常活动
- 适用：知识难以言表时
- 风险：被同化、失去客观立场

**原型与仿真**：

- 目标：明确含糊需求、简化文档、获得早期反馈
- 优势：直观有效的沟通工具

#### 2. 竞争性需求分析（NABCD框架）

- **Need**：市场需求
- **Approach**：独特方法
- **Benefits**：用户收益
- **Competition**：竞争优势
- **Delivery**：交付推广

#### 3. A/B测试

应用场景：已有用户基础，不确定UI改进是否受欢迎

步骤：

1. 确定两种UI方案
2. 确定衡量标准
3. 选择5-10%用户
4. 收集数据、分析、得出结论

#### 4. 需求验证方法

- **评审（Review）**
- **原型化（Prototyping）**
- **模型验证（Model validation）**
- **确认测试（Acceptance Tests）**

**最佳实践**：原型验证 + 测试验证识别率高，成本较低

#### 5. 需求文档

**软件需求规格说明（SRS）**：

- 具有一定法律效力的合同文档
- 清楚描述软件需要做什么、不能做什么
- 作为后续评估和变更的基准

**组织形式**：

- 按外部环境情况组织
- 按系统特征组织
- 按用户类型组织
- 按子系统划分组织

**SRS风格**：

- 描述性自然语言文本
- 用户故事
- 从用例模型产生
- 从需求数据库生成

## 第8周：顺序图与状态图

**文件名**：`第8周_顺序图+状态图.md`

### 🎯 核心主题

UML 行为建模中的 **顺序图** 与 **状态图**：前者描述对象如何围绕某个场景进行消息交互，后者描述核心对象在生命周期中的状态变化。

### 📖 主要内容

#### 1. 顺序图（Sequence Diagram）

- 表达**单个情景实例**中的对象协作行为
- 可从用例图和用例描述中抽取，用来细化场景流程
- 适合分析参与者、边界对象、控制对象、实体对象之间的消息流
- 建模时应关注关键交互、消息参数、控制焦点与条件分支

#### 2. 顺序图的建模规范

- 分析阶段不要过早混入设计实现细节
- 参数尽量写业务含义，不要只写类型
- 图过大时用 `ref` 做引用拆分
- 有条件分支时应使用组合控制框，如 `alt`
- 可通过控制焦点表示递归、嵌套调用和执行区间

#### 3. 状态图（State Diagram / State Machine Diagram）

- 描述某个类或核心对象在整个生命周期中的状态变化
- 核心元素包括：状态、事件、迁移、动作、初态、终态
- 适用于状态显著、行为复杂的核心对象，而非所有类

#### 4. 状态图的建模规范

- 迁移通常由“事件 + 警戒条件 + 动作”组成
- `entry` / `exit` / `do` 用于表达状态内动作
- 可使用组合状态、历史状态表达复杂流程与恢复逻辑
- 同源同事件的多条迁移应保证警戒条件互斥

#### 5. 与其他 UML 图的关系

- 顺序图用于把用例落实到具体交互过程
- 状态图中的事件通常对应顺序图中对象收到的输入消息
- 状态图中的事件、动作通常能映射到类图中的操作定义

#### 6. 对 `lab3` 的直接帮助

- 为“智能城市生成系统”设计报告中的**顺序图**章节提供建模方法
- 为报告中的**状态图**章节提供对象选择思路和状态迁移规范
- 可据此选择“城市生成任务”“方案审核流程”“仿真任务”等对象进行建模
