# 软件工程第四次作业测试报告

## 1. 题目与问题定义

本次作业题目为“滑动窗口最大值实现”。

给定一个整数数组 `nums` 和窗口大小 `k`，滑动窗口从数组最左侧向右侧逐步移动，每次移动一位。对于每一个窗口，需要求出窗口范围内的最大值，并将这些最大值组成结果数组。

## 2. 算法设计与实现思路

本作业实现了两种求解方式：

- 朴素解法：对每个窗口直接求最大值，用于正确性校验与性能对比
- 优化解法：使用单调队列维护窗口中的候选最大值下标

代码结构上，将输入校验、朴素解法和优化解法拆分为独立函数，便于测试、维护和后续扩展。

### 2.1 功能需求

程序需要完成以下功能：

- 接收整数数组 `nums` 和窗口大小 `k`
- 计算滑动窗口每次移动后的窗口最大值
- 返回由所有窗口最大值组成的结果列表
- 对非法输入给出明确异常

### 2.2 输入输出约定

- 输入：
  - `nums: list[int]`
  - `k: int`
- 输出：
  - `list[int]`

主接口定义为 `max_sliding_window(nums, k)`，另提供 `max_sliding_window_bruteforce(nums, k)` 作为朴素对照实现。

### 2.3 非法输入处理约定

程序对非法输入采用显式校验，规则如下：

- 当 `nums` 不是列表时，抛出 `TypeError`
- 当 `nums` 中存在非整数元素时，抛出 `TypeError`
- 当 `k` 不是整数时，抛出 `TypeError`
- 当 `k <= 0` 时，抛出 `ValueError`
- 当 `k > len(nums)` 时，抛出 `ValueError`
- 当 `nums` 为空列表时，抛出 `ValueError`

单一职责原则的含义是：一个模块、类或函数应该只负责一项明确的职责。这样做的好处是，当需求发生变化时，变化会尽量被限制在单一位置，不会牵连太多无关代码，从而提高代码的可维护性和可测试性。

## 6. 错误与异常处理

错误与异常处理是本次作业中的一个重点。滑动窗口最大值的核心算法本身并不复杂，但如果输入不合法、边界条件不完整，程序就可能在深层逻辑中才暴露错误。这种错误虽然也会报出来，但报错位置通常不明确，不利于定位问题，也不利于后续维护。

本作业采用的处理思路是：在算法入口处统一完成输入合法性检查，把“正常计算逻辑”和“异常处理逻辑”分离。这样做有两个直接好处：

- 核心算法函数内部只需要关注正确输入下的求解过程，逻辑更清晰
- 错误能够在最靠近入口的位置被发现，异常原因也更明确

程序显式处理了以下错误情况：

- `nums` 不是列表
- `nums` 中含非整数元素
- `k` 不是整数
- `k <= 0`
- `k > len(nums)`
- `nums` 为空列表

对于这些错误，程序没有使用笼统的报错方式，而是按错误性质进行细分：

- 当输入类型不符合要求时，例如 `nums` 不是列表、`nums` 中含非整数元素、`k` 不是整数，程序抛出 `TypeError`
- 当输入类型正确但数值范围不合法时，例如 `k <= 0`、`k > len(nums)`、`nums` 为空列表，程序抛出 `ValueError`

这种区分方式的意义在于：`TypeError` 反映的是“传进来的东西类型不对”，而 `ValueError` 反映的是“类型对了，但取值不合法”。这样不仅更符合 Python 的异常使用习惯，也使测试用例和后续维护时的问题定位更加直接。

此外，本作业没有使用裸 `except` 来笼统吞掉所有异常。这是因为裸 `except` 容易掩盖真实错误来源，也会降低调试效率。当前实现选择在输入层面做显式校验，并让异常按照明确类型抛出，这样既满足课程中“针对具体异常类型处理”的要求，也保证了代码行为可预测。

## 7. 算法复杂度分析

### 7.1 朴素解法

朴素解法的思路是：当窗口每向右移动一次，就重新扫描当前窗口中的 `k` 个元素，并调用 `max()` 求出该窗口的最大值。

设输入数组长度为 `n`，窗口大小为 `k`，则一共需要处理的窗口个数为：

`n - k + 1`

对于每一个窗口，朴素解法都需要重新遍历这 `k` 个元素求最大值，因此单个窗口的代价为 `O(k)`。于是总时间复杂度为：

`O((n - k + 1) * k)`

当只保留主导项时，可以记为：

- 时间复杂度：`O(nk)`

空间方面，朴素解法在求每个窗口最大值时没有额外维护复杂的数据结构，除输出结果外只使用了常数个辅助变量，因此：

- 空间复杂度：`O(1)`（不计输出结果）

朴素解法的主要问题在于：相邻窗口之间存在大量重叠元素，但程序仍然会反复扫描这些元素，因此重复计算较多。

### 7.2 优化解法

优化解法使用单调队列维护“当前窗口内仍然有资格成为最大值的元素下标”。队列中的下标对应值始终保持单调递减，因此队首元素始终对应当前窗口最大值。

在遍历数组过程中，每个元素会经历以下操作：

1. 最多入队一次；
2. 最多因“滑出窗口”从队首移出一次；
3. 最多因“比新元素小”从队尾移出一次。

也就是说，虽然代码中存在 `while` 循环，但从整体上看，每个元素不会被无限次处理，而是在整个算法执行过程中至多进入队列一次、离开队列一次。因此所有入队、出队操作的总次数与 `n` 成正比。

于是优化解法的总时间复杂度为：

- 时间复杂度：`O(n)`

空间方面，单调队列中最多只会保存当前窗口范围内的若干下标，队列长度不会超过窗口大小 `k`，因此：

- 空间复杂度：`O(k)`

这种复杂度改进的本质在于：程序不再对每个窗口重复扫描全部元素，而是通过单调队列保留“可能成为最大值”的候选元素，从而把重复计算压缩到最低。

### 7.3 两种解法复杂度对比

两种解法的复杂度差异可以概括如下：

- 朴素解法：每个窗口独立求最大值，重复扫描窗口内部元素，时间复杂度为 `O(nk)`
- 优化解法：用单调队列复用相邻窗口之间的信息，时间复杂度降为 `O(n)`

当 `k` 较大或者 `n` 持续增大时，`O(nk)` 和 `O(n)` 之间的差距会迅速扩大，这也是后续性能测试中优化解法明显更快的根本原因。

### 8.1 优化前的实现思路

优化前采用的是朴素解法。它的基本思路是：每当窗口向右滑动一次，就重新截取当前窗口中的 `k` 个元素，并直接调用 `max()` 求最大值。

这种方法实现简单，也便于作为正确性对照，但它存在一个明显问题：窗口之间高度重叠，相邻两个窗口只相差一个移出元素和一个移入元素，可朴素解法仍然会把整个窗口重新扫描一遍，因此产生了大量重复计算。

这种做法的目的不是只得到一个“快还是慢”的结论，而是让优化具有证据基础：先确认哪种实现更快，再分析快慢差异来自哪里。

### 8.3 我是如何进行优化的

本次优化的核心不是调整语法细节，而是替换算法和数据结构。

朴素解法的主要问题是：每次窗口移动后都重新扫描窗口内部全部元素，因此时间复杂度为 `O(nk)`。要优化这个过程，就需要避免重复扫描窗口内部的旧元素。

我采用的优化方法是单调队列。具体思路如下：

- 队列中不直接保存元素值，而是保存元素下标
- 队列中的下标对应值保持单调递减
- 当新元素进入窗口时，移除队尾所有比它小的元素，因为这些元素在当前窗口和后续窗口中都不可能再成为最大值
- 当窗口左端滑动时，如果队首下标已经不在窗口范围内，就将其移除
- 这样，队首下标始终对应当前窗口最大值

这种优化的关键在于：每个元素最多只会进入队列一次、移出队列一次，因此整体时间复杂度可以降到 `O(n)`。

### 8.4 为什么说这是有效优化

这次优化之所以有效，不是因为代码“写得更短”，而是因为减少了重复计算。

- 在朴素解法中，同一个元素可能会被多个相邻窗口反复比较
- 在单调队列解法中，一个元素一旦被判定不可能再成为最大值，就会被及时移除，不再参与后续比较

也就是说，优化的本质是利用数据结构保存“仍然有资格成为最大值的候选元素”，而不是每次都从头计算。

### 8.5 优化结果分析

从测试结果可以看出，随着数据规模增大，优化解法和朴素解法之间的差距会越来越明显。这说明当前优化并不是偶然的常数项改进，而是复杂度层面的改进。

进一步的 `cProfile` 结果显示，优化解法的主要耗时仍集中在主算法函数本身，而不是浪费在无关逻辑上。这说明当前实现已经把性能开销集中在真正需要执行的核心计算上，优化方向是合理的。

为了进一步观察核心函数内部的耗时分布，本作业又使用 `line_profiler` 对 `max_sliding_window` 做了逐行分析。相关脚本和结果文件分别为 [analysis/line_profile_experiment.py](../analysis/line_profile_experiment.py)、[analysis/line_profile_result.txt](../analysis/line_profile_result.txt) 和 [analysis/line_profile_result.lprof](../analysis/line_profile_result.lprof)，运行命令为 `python3 -m analysis.line_profile_experiment`。测试参数为 `n = 10000`、`k = 100`。结果表明，`validate_inputs(nums, k)` 约占 `12.1%`，维护单调队列的 `while window_indexes and nums[window_indexes[-1]] <= value` 约占 `21.8%`，将窗口最大值写入结果的 `result.append(nums[window_indexes[0]])` 约占 `14.0%`。这说明优化解法的主要成本确实集中在队列维护、窗口边界判断和结果输出这些核心步骤上，而不是分散在无关辅助逻辑中。

- 朴素解法每次窗口滑动都重新求最大值，存在重复计算
- 优化解法通过单调队列保存候选最大值下标，避免重复遍历窗口内部元素
- 因此整体时间复杂度由 `O(nk)` 降为 `O(n)`

性能分析说明，优化的关键不在于语法层面的微调，而在于数据结构和算法选择。

### 9.1 黑盒测试设计

黑盒测试不依赖程序内部实现细节，而是依据题目需求、输入约束和输出约定设计测试用例。本作业中的黑盒测试主要包含以下三类：

1. 有效等价类：为正常、合法输入设计代表性样例，如标准示例、严格递增、严格递减、全相同元素、含负数等，用于验证程序是否实现了题目要求的基本功能。
2. 无效等价类：对 `nums=None`、非列表输入、元素类型非法、`k` 非整数等不合理输入单独设计测试，用于验证程序的容错与异常处理能力。
3. 边界值与健壮性测试：重点测试 `k=1`、`k=len(nums)`、单元素数组、`k=0`、`k<0`、`k>len(nums)`、空列表等边界和越界场景。这里既覆盖了边界值分析，也体现了健壮性测试中“略小于最小值、略大于最大值”的思想。

### 9.2 白盒测试设计

白盒测试关注程序内部逻辑结构，强调关键分支、关键路径和错误处理路径是否被测试触达。本作业中的白盒测试主要包括：

1. 输入校验分支测试：验证 `validate_inputs` 中的类型判断、空列表判断和窗口范围判断是否都能正确进入对应分支。
2. 窗口边界变化测试：验证窗口左边界滑出和右边界进入时，队列状态更新是否正确。
3. 最大值更新路径测试：验证原最大值滑出窗口后，程序能否正确选择新的窗口最大值。
4. 一致性互验测试：将朴素解法与优化解法在同一输入上的结果逐一比较，用于辅助验证主算法内部逻辑没有偏差。
5. `mock` 隔离依赖测试：在文本样例读取测试中，使用 `unittest.mock` 模拟 `Path.read_text` 的返回值，隔离真实文件系统依赖，验证样例解析逻辑本身是否正确。

测试中使用了 `unittest` 的 `assertEqual` 和 `assertRaises` 等断言方法，以验证结果与异常行为是否符合预期。
