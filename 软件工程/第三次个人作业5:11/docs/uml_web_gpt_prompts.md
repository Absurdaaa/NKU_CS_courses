# 智能城市生成系统 UML 网页版 GPT 生成提示词

## 说明

这份文档基于 [需求分析报告.tex](/Users/linshangjin/NKU_CS_courses/软件工程/第三次个人作业5:11/ref/需求分析报告.tex) 的内容整理，目标不是解释 UML 基础概念，而是给出可以直接复制到网页版 GPT 中使用的详细提示词，让它帮你生成更稳定、更贴题的 UML 图描述或 PlantUML 代码。

为了让 8 张图保持统一，所有提示词都遵循以下项目背景：

- 系统名称：智能城市生成系统
- 核心目标：在 Blender 插件执行环境基础上，结合程序化建模和大语言模型，实现三维城市场景生成、布局调整、资产替换、动态仿真和多角色协同管理
- 三类核心用户：场景建模师、行业分析师、系统管理员
- 核心创新点：支持自然语言、草图、点线集、参数表单等多模态输入，由 LLM 解析后生成结构化任务，再调用 Blender 插件执行
- 关键设计边界：LLM 只负责理解用户意图、抽取对象和关系、生成结构化任务建议，不直接替代 Blender 插件执行几何建模
- 系统关键能力模块：
  - 用户与权限管理
  - 插件交互与任务调度
  - 场景生成与资产替换
  - 布局与生态控制
  - 智能交互与多模态解析
  - 动态仿真与结果展示
- 关键数据对象：
  - User
  - Role
  - Permission
  - Project
  - Scene
  - Asset
  - SketchImage
  - LayoutSet
  - TaskConfig
  - LLMTask
  - SimObject
  - OperationLog

建议你每次在网页版 GPT 里提问时，都先说明：

- 你希望输出的是“图的结构说明”还是“PlantUML 代码”
- 图中标签全部使用中文
- 图中内容要贴合“智能城市生成系统”，不要泛化成普通管理系统

## 1. 用例图提示词

### 适用目标

用于让 GPT 帮你生成系统的用例图结构或 PlantUML 代码。

### 可直接复制的提示词

```text
请根据以下软件需求，帮我生成“智能城市生成系统”的 UML 用例图，输出 PlantUML 代码，并保证图中所有文字为中文。

项目背景：
这是一个智能城市生成系统，运行基础是 Blender 插件执行环境，并结合大语言模型进行自然语言和多模态输入解析。系统不仅是一个三维建模工具，还包括任务调度、资源管理、动态仿真、权限治理和日志审计能力。

系统有三类核心用户：
1. 场景建模师：负责创建、调整和导出三维城市场景，重点关注场景生成效率、参数控制、资产替换、布局编辑和智能交互。
2. 行业分析师：负责查看场景结果、运行动态仿真、比较不同方案并导出分析结果，更关注结果展示和方案比较，不承担复杂建模。
3. 系统管理员：负责用户、角色、权限、资源、模型服务、插件状态和日志审计，重点关注系统治理和稳定运行。

系统主要功能包括：
1. 登录认证
2. 项目管理
3. 场景生成
4. 资产替换
5. 布局编辑
6. 草图解析
7. 自然语言建模
8. 多模态任务解析
9. 运行动态仿真
10. 查看结果
11. 方案比较
12. 导出结果/导出报告
13. 用户管理
14. 权限配置
15. 资源管理
16. 日志审计
17. 系统监控

绘图要求：
1. 用例图必须有系统边界框，名称为“智能城市生成系统”。
2. 必须只保留三类角色：场景建模师、行业分析师、系统管理员。
3. “自然语言建模”和“多模态任务解析”应体现为系统创新功能，但不要让 LLM 单独作为 Actor。
4. 需要适当使用 include 或 extend 表示关系，例如“草图解析”与“布局编辑”、“自然语言建模”与“场景生成”的关系。
5. 图中不要出现数据库、Blender、LLM 服务作为用户角色。
6. 图的复杂度适中，适合作为课程作业软件设计报告中的正式 UML 用例图。

请直接输出可渲染的 PlantUML 代码，不要解释。
```

### 这张图的重点

- 强调三类角色差异
- 强调建模师是核心使用者
- 强调分析师偏结果消费
- 强调管理员偏治理维护
- 强调智能交互是“场景生成”的增强能力

## 2. 活动图提示词

### 适用目标

用于生成“从多模态输入到 Blender 插件执行”的主活动流程图。

### 可直接复制的提示词

```text
请根据以下需求，生成“智能城市生成系统”的 UML 活动图，输出 PlantUML 代码，图中全部使用中文。

我要表达的业务主线是：场景建模师通过文本、草图、点线集或参数表单表达设计意图，系统将其解析为结构化任务，在用户确认后调用 Blender 插件执行，最后返回场景结果并保存版本。

项目关键背景：
1. 系统支持多模态输入，包括自然语言、草图、点线集和参数表单。
2. LLM 的职责是识别用户意图、抽取对象、数量、空间关系和参数建议，并生成结构化任务建议。
3. Blender 插件负责真正的场景生成、对象替换、布局调整和场景文件更新。
4. 系统不能让 LLM 直接执行建模，必须先展示结构化结果给用户确认。
5. 如果输入存在歧义、上下文不足、场景条件不满足或资源不可用，系统必须给出提示，而不是直接执行。
6. 执行完成后系统要保存场景版本、任务记录和日志。

请围绕下面这条主流程绘制活动图：
1. 用户输入文本/草图/参数
2. 系统接收输入
3. 输入规范化
4. LLM 解析或规则解析
5. 生成结构化任务建议
6. 判断是否有歧义或约束冲突
7. 若有问题，提示用户补充或修正
8. 用户确认任务
9. 任务下发 Blender 插件
10. 插件执行
11. 判断是否执行成功
12. 若失败，返回错误原因并允许重新配置
13. 若成功，保存场景版本和日志
14. 展示结果并结束

绘图要求：
1. 必须有开始节点和结束节点。
2. 必须体现判定节点，例如“是否存在歧义”“是否满足执行条件”“执行是否成功”。
3. 必须体现回路，不能画成一条无分支直线。
4. 图中不要出现无意义细节，例如数据库字段。
5. 这是一张课程作业用的 UML 活动图，不是普通业务流程图，要体现控制逻辑。

请直接输出可渲染的 PlantUML 代码，不要额外解释。
```

### 这张图的重点

- 体现“解析前不能执行”
- 体现“确认后再执行”
- 体现“失败可回退”
- 体现“版本与日志留痕”

```text

系统背景：
该系统基于 Blender 插件执行三维城市场景生成与修改任务，并通过 LLM 支持自然语言和多模态输入解析。系统支持角色权限控制、项目与场景版本管理、资产管理、布局控制、动态仿真、任务调度和日志审计。

请围绕以下核心类构造类图：

用户与权限相关：
- User
- Role
- Permission

项目与场景相关：
- Project
- SceneVersion
- SceneObject

任务与智能解析相关：
- Task
- StructuredCommand
- ParseResult
- PromptContext
- ConfirmationRecord

资源相关：
- Asset
- AssetCategory
- AssetConstraint

布局相关：
- LayoutSet
- ControlPoint
- ControlLine
- Region
- SketchImage

仿真相关：
- SimulationPlan
- SimObject

日志与治理相关：
- OperationLog
- ServiceConfig

请在图中体现以下关系：
1. User 与 Role 关联，Role 与 Permission 关联
2. Project 聚合多个 SceneVersion
3. SceneVersion 关联多个 SceneObject
```

### 这张图的重点

- 体现项目-场景版本-任务的主线
- 体现 LLM 解析到结构化任务的桥梁作用
- 体现布局对象和资产对象不是一回事
- 体现日志和治理对象的存在

## 4. 顺序图提示词

### 适用目标

用于生成“自然语言输入触发建模”的时序交互图。

### 可直接复制的提示词

```text
请根据以下需求，生成“智能城市生成系统”的 UML 顺序图，输出 PlantUML 代码，图中全部使用中文。

我要表达的典型场景是：
场景建模师输入自然语言或多模态指令，例如“在城市东侧新增滨水公园，并增加沿湖道路和两艘动态船只”，系统先调用 LLM 解析意图，再进行约束检查与用户确认，最后调用 Blender 插件执行任务，并保存结果和日志。

系统关键约束：
1. LLM 只负责解析和生成结构化任务建议，不直接执行场景建模。
2. 在正式执行前，系统必须向用户展示任务解释结果，并允许用户确认或修改。
3. 若当前场景缺少必要条件，例如没有水域却要求添加船只，系统要在执行前提示问题。
4. 执行完成后要保存项目版本、任务记录和日志。

请使用以下参与者：
- 场景建模师
- 主系统界面
- 任务调度服务
- LLM 解析服务
- 约束检查器
- Blender 插件适配器
- Blender 插件
- 项目/日志存储

请按以下消息顺序组织顺序图：
1. 场景建模师提交自然语言或多模态输入
2. 主系统界面向任务调度服务发起解析请求
3. 任务调度服务调用 LLM 解析服务
4. LLM 返回 ParseResult
5. 任务调度服务调用约束检查器
6. 约束检查器返回校验结果
7. 主系统界面向用户展示结构化任务建议
8. 用户确认任务
9. 主系统界面请求任务调度服务下发任务
10. 任务调度服务调用 Blender 插件适配器
11. 插件适配器调用 Blender 插件执行任务
12. Blender 插件返回执行结果
13. 任务调度服务保存版本与日志
14. 主系统界面刷新结果视图

绘图要求：
1. 必须体现返回消息，不要只有单向调用。
2. 必须突出“用户确认”步骤。
3. 必须体现约束检查步骤。
4. 不要把顺序图画成简单流程图，重点是对象间按时间顺序交互。
5. 图中标签用中文，方法名可以保留简洁英文。

请直接输出 PlantUML 代码，不要解释。
```

### 这张图的重点

- 先解析，再检查，再确认，再执行
- LLM 与 Blender 插件是两个完全不同的参与者
- 存储不仅保存结果，还保存日志

## 6. 状态图提示词

### 适用目标

用于生成 `Task` 对象生命周期状态图。

### 可直接复制的提示词

```text
请根据以下需求，为“智能城市生成系统”生成一张 UML 状态图，输出 PlantUML 代码，图中全部使用中文。

我希望状态图的核心对象是“任务 Task”，因为这个系统的核心机制是：用户输入 -> 结构化任务生成 -> 用户确认 -> 插件执行 -> 结果保存。任务是连接用户输入、LLM 解析、插件执行、日志记录和场景版本的中心对象。

系统对任务的要求包括：
1. 用户提交输入后，系统生成任务。
2. LLM 解析完成后，任务进入待确认状态。
3. 用户可以确认任务，也可以取消任务。
4. 确认后的任务进入排队或待执行状态。
5. Blender 插件执行时进入运行中状态。
6. 执行成功后进入成功状态。
7. 执行失败后进入失败状态，并允许重试或终止。
8. 任务结束后可以归档，用于日志审计和历史追踪。

请至少包含以下状态：
- 已创建
- 待确认
- 已确认
- 排队中
- 执行中
- 执行成功
- 执行失败
- 已取消
- 已归档

如果你认为合适，也可以加入“重试中”状态。

请体现以下状态迁移触发条件：
- 生成任务建议
- 用户确认
- 用户取消
- 进入队列
- 开始执行
- 执行成功
- 执行失败
- 重试任务
- 归档结果

绘图要求：
1. 必须包含初始状态和终止或收束逻辑。
2. 触发条件要写清楚，不能只画箭头。
3. 状态名必须是状态，不是动作。
4. 图中要体现该系统“确认后执行”的控制特点。

请直接输出 PlantUML 代码，不要解释。
```

### 这张图的重点

- 任务不是提交后立刻执行
- “待确认”是这个系统区别于普通自动化流程的重要状态
- “失败”“取消”“归档”都属于正常设计的一部分

## 使用建议

如果网页版 GPT 一次输出的代码不稳定，可以继续追加这类补充要求：

```text
请检查 PlantUML 语法是否可直接渲染，避免引用未定义组件。
请控制图复杂度，不要让连线过多交叉。
请保证所有节点、参与者、组件和类都已定义。
请不要省略 @startuml 和 @enduml。
```

如果你不想让它直接出代码，而是先帮你“规划图”，可以改成：

```text
不要直接输出 PlantUML 代码。请先列出这张图应该包含的参与者/类/组件/状态/关系，并给出结构草稿。
```

如果你后面要继续批量生成 8 张图，最稳的做法是：

1. 先用这里的提示词让网页版 GPT 生成结构草稿
2. 再要求它输出 PlantUML 代码
3. 最后把代码丢到 PlantUML 环境里渲染

这样比一步到位更不容易出错。
